# Self-hosted backend notes

Jot's server uses Node 24 and SQLite. `JOT_DATA_DIR` selects its data directory (default `.jot-data` in the working directory). Stop the server before copying the whole directory for a backup, or use a SQLite-aware backup method. Before upgrading, back up the database and stop all old server instances; mixed-version writers are not supported during schema migration. Keep backups private. No external account, SMTP provider, or hosted service is required.

Backend unit/integration tests run with `npm test`. For production HTTP and real client-adapter smoke tests against disposable databases and synthetic accounts, run `npm run build && node tests/backend-live.mjs && node --import tsx tests/backend-client-live.mts`. The latter uses fake IndexedDB, not a browser.

The first local account can register by default. To onboard additional users, an operator must explicitly set `JOT_ALLOW_REGISTRATION=true`; set it to `false` to disable all registration. There is no default password. Passwords require at least 12 characters. Sharing grants access to an **existing** account; it does not send an email invitation.

The default trusted browser origin is exactly `http://localhost:3000`. Set `JOT_APP_ORIGIN` to the exact browser origin (including non-default port) when using a different hostname or port, even on localhost; for example, `http://127.0.0.1:3215`. Origin validation never trusts Host or forwarded-host headers. Use HTTPS and a properly configured reverse proxy for non-local access; set `JOT_SECURE_COOKIES=true` behind TLS termination. The process uses bounded login/registration throttles and a concurrent password-hashing limit, but these are process-local, not a distributed abuse defense. Without a trusted proxy, attempts share an account-level bucket, so repeated failures can temporarily lock out that account. For a proxy-sanitized client IP, set `JOT_TRUST_PROXY_IP_HEADER` to a header that **your trusted proxy overwrites with exactly one IP address**; account buckets then include the IP, while forwarded headers remain ignored by default. Add proxy-level rate limits for public deployments.

Attachments are limited to 10 MiB each. The default owner quota is 1 GiB of live bytes (`JOT_MAX_USER_STORAGE_BYTES`) and 10,000 lifetime attachment records (`JOT_MAX_USER_ATTACHMENT_RECORDS`), including deletion tombstones. Tombstones are retained to prevent deleted IDs from reappearing. These limits can be raised deliberately by the operator. Synchronization receipts contain no note body, are retained for at most 30 days and 10,000 per account, and old retries safely become conflicts rather than overwriting newer content.

Each owner also has default limits of 10,000 notes, 1,000 notebooks, 50,000 live comments, and 256 MiB of combined logical content bytes (UTF-8, including JSON encoding for notes and notebooks). Trashed notes and notebooks still count. Operators can set `JOT_MAX_USER_NOTES`, `JOT_MAX_USER_NOTEBOOKS`, `JOT_MAX_USER_COMMENTS`, and `JOT_MAX_USER_CONTENT_BYTES` to non-negative integer limits. Quota failures return 413 without replacing existing content; after a limit is lowered, existing content can still be reduced.

## Optional server content encryption

For a **fresh** data directory only, set `JOT_ENCRYPTION_KEY` before the first server start to exactly 64 hexadecimal characters representing a securely generated random 256-bit key. Generate it once with a trusted system random source (for example `openssl rand -hex 32`), store it securely **separately from the database backup**, and provide the same key on every restart. Do not put it in source control. Losing the key makes encrypted content unrecoverable. Wrong or missing keys are rejected; an existing plaintext database is not silently converted. There is no built-in key rotation or plaintext-to-encrypted migration.

In this mode, note and notebook contents, comment text, attachment filenames and bytes are encrypted with AES-256-GCM before SQLite writes them. Account emails, IDs, access relationships, timestamps, logical content byte counts, attachment MIME types and sizes, and other operational metadata remain plaintext. The server can decrypt content while running: this is **not end-to-end encryption**. Browser/IndexedDB copies and user exports are not encrypted by this server setting. Protect transport with HTTPS, protect devices separately, and back up both data and key.

This mode helps protect content from read-only storage theft when the key is kept separate. It does not protect against a compromised running server or someone who can write the authentication, ownership, or ACL database; those plaintext records are not tamper-proof. Restrict database write access and protect backups.
